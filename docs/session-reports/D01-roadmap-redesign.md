# D01 — 세션 로드맵 재설계

**목적:** 기존 미진행 세션을 폐기하고 사용자 우선순위에 맞춰 다음 개발을 설계한다.

**요약:** 치명적 버그 분석·개선, 공용 잔액·메인 메뉴, 바카라, 사용성 개선의 N01~N06을 정의했다. 이번 작업은 문서 설계와 제한된 정적 소스 확인이며 기능 구현·앱 테스트는 수행하지 않았다.

## 1. 범위와 결정

사용자는 기존에 작성한 세션 중 진행되지 않은 내용을 전부 폐기하고 새로 설계하도록 요청했다. 우선순위는 치명적 버그 개선, 메인 메뉴·바카라 추가, 기타 사용성 개선이다. 추가로 이번에는 설계만 수행한다고 확인했다.

대화에서 확정한 제품 방향은 모든 게임의 공용 잔액, 판 중 메뉴 이동 금지, 메인 메뉴의 초기 금액 $100 새 시작, 기본 수수료 바카라, 한 곳 베팅, 최근 P·B·T 한 줄이다. 상세 계약은 [메인 제품 설계](../main/product-design.md#5-메인-메뉴와-공용-잔액의-신규-설계)·[바카라 제품 설계](../games/baccarat/product-design.md)에 둔다.

미완료 판이 있으면 해당 게임으로 시작하고 없으면 메뉴로 시작하는 흐름, 판이 없으면 잔액이 남아 있어도 메뉴에서 확인 후 새 시작, 바카라 8덱·최근 기록 20개·센트 반올림은 위 방향에 맞춘 설계 기본값이다. 향후 사용자 피드백으로 변경할 수 있다. 초기 $100은 현재 `src/core/game-state.ts`의 10,000센트와도 일치하며, 대화 중 제안한 $500은 채택하지 않았다.

## 2. 소스 사전 검토

메인 창·IPC·시작/종료, GameStore 명령·저장 경로, SessionRepository, Preload·공유 계약, Renderer의 구독·금액 입력, 블랙잭 엔진·정산·슈의 관련 코드와 일부 기존 테스트를 읽었다. 전체 경로의 실행 검증이나 모든 소스의 결함 감사를 완료한 것은 아니다.

### 확인한 구조와 방어 코드

| 근거 | 확인한 사실과 설계 영향 |
| --- | --- |
| `src/main/main.ts`의 `start`·IPC 등록 | 블랙잭 GameStore 하나와 블랙잭 전용 저장소를 직접 연결한다. 여러 게임용 공용 작성자·라우팅은 새 작업이다. |
| `src/shared/contracts.ts`, `src/preload/preload.ts` | `window.blackjack`에 창 API와 게임 API가 함께 있다. gameId를 판별하는 앱 공통 API로 전환해야 한다. |
| `src/main/persistence/session-repository.ts` | 저장 schemaVersion 1은 블랙잭 타입을 직접 검증한다. 기존 파일을 임의로 바카라에 재사용할 수 없다. |
| `src/main/game/game-store.ts` | busy·revision·명령 캐시, 저장 성공 후 상태 공개, 실패 후보 재시도, 내부 딜러 진행이 이미 있다. 공용 상태에서도 이 보존 원리를 활용한다. |
| `src/main/main.ts`의 `requestSingleInstanceLock` | 단일 인스턴스 잠금이 있다. 중복 실행 방어 부재라는 초기 추정은 확인 후 철회했고 결함 후보에 포함하지 않는다. |
| `src/main/ipc/trust.ts` | sender·최상위 frame·정확한 URL을 확인한다. 신규 API에서도 기존 신뢰 경계를 유지한다. |
| `src/core/game-state.ts`, `shoe.ts` | 현재 초기 잔액 $100, 블랙잭 6덱은 명시적 상수다. 공용 초기 금액은 유지하고 바카라 슈 규칙은 분리한다. |

### N01에서 평가할 후보

| 후보 | 소스에서 관찰한 경로 | 필요한 판단 |
| --- | --- | --- |
| Renderer 종료 후 복구 | `main.ts`의 `render-process-gone`은 숨김·로그, 트레이 reveal은 기존 창 표시이며 재생성하지 않는다. | 실제 프로세스 종료 후 플레이·트레이 복구가 어떤 상태인지 재현하고 치명도 판단. 구 S16 전체 설계를 자동 채택하지 않는다. |
| 시작 시 파일 I/O 실패 | 저장 읽기의 ENOENT 외 오류는 throw, `start()` 실패는 로그 후 종료이며 트레이 생성 전에 실패할 수 있다. | 재시도 가능한 오류 조건과 실제 사용자 복구 가능성을 확인. 권한 문제 자체를 제품 결함으로 단정하지 않는다. |
| 저장 실패와 종료의 경계 | 저장 중 종료는 idle을 기다리며 pending이면 복원한다. busy가 끝난 뒤 명시적 종료는 마지막 확정 상태만 남길 수 있다. | 확정된 금액/판 손실 여부와 사용자 안내를 실제 실패 조건에서 확인. 미확정 후보 폐기를 곧바로 중복 정산·데이터 손상으로 보고하지 않는다. |

**확정·재현된 치명적 버그는 이번 설계 작업에서 없음.** 위 항목은 조사 후보와 알려진 구현 한계다. N01에서 검증하고 문제가 없으면 수정 세션을 만들지 않는다.

## 4. 검증과 한계

문서의 상대 경로·목차 앵커와 초기 금액·진행 중 이동 금지·새 세션 번호·폐기 상태의 일관성을 점검했다. 31개 문서의 로컬 Markdown 링크 481개가 파일·앵커로 연결됐으며, `git diff --check`에서 공백 오류가 없었다. 변경 파일은 모두 Markdown 문서다.

앱 소스·테스트 코드를 수정하지 않았고, 앱 실행·패키징·E2E·하위 테스트는 실행하지 않았다. 과거 테스트 통과 수를 이번 검증 결과로 재사용하지 않는다. 바카라·메뉴·공용 저장은 설계만 있으며 실제 구현·성능·OS 동작을 보장하지 않는다.
