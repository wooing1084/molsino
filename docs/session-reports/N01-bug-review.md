## 1. 점검 범위와 결론

Main 시작·종료·창·IPC, GameStore의 명령/정산/저장 실패, SessionRepository의 파일 처리, Renderer 상태 구독·입력·오류 UI, 블랙잭 규칙·정산·슈와 관련 테스트를 확인했다. 의심 경로는 현재 소스로 다시 만든 macOS 패키지에서 격리된 저장 데이터로 재현했다.

| 항목 | 판단 | 제안 |
| --- | --- | --- |
| BUG-01 Renderer 장애 처리의 추가 예외 | 재현된 결함. 창 상태 변경과 복원 모두 실패 | 조사 기록으로 보존, 수정 일정 제외 |
| BUG-02 허용된 큰 베팅의 정산 오류와 잘못된 재시도 | 재현된 결함. 일반 플레이에서는 만나기 어려운 극단 금액 조건 | 조사 기록으로 보존, 바카라 착수 조건에서 제외 |

일반 플레이의 정산 오류나 확정된 잔액 손실은 조사 범위에서 발견하지 못했다. 버그가 전혀 없다는 증명은 아니다. BUG-01은 Renderer가 왜 처음 종료되는지를 찾아낸 결과가 아니라, 종료된 뒤 기존 처리 코드가 추가로 실패한다는 결과다.

## 2. BUG-01 — Renderer 종료 처리와 복원에서 Main 예외

### 발생 조건과 재현

1. 격리된 userData에서 앱을 시작해 $1을 딜한다. 플레이어 차례, revision 1, 잔액 $99 상태를 만든다.
2. Playwright의 Electron Main 접근으로 해당 테스트 창의 `webContents.forcefullyCrashRenderer()`를 호출한다.
3. `render-process-gone` 처리와 이후 `app.emit('activate')`를 통한 기존 reveal 경로를 관찰한다. 이 경로는 트레이 복원·전역 토글이 사용하는 reveal과 같다. 실제 트레이 클릭이나 물리 키 입력은 수행하지 않았다.

실제 오류:

```text
Error: Render frame was disposed before WebFrameMain could be accessed
```

Main이 먼저 발생시킨 예외 때문에 뒤에 추가한 render-process-gone 관찰 리스너까지 실행되지 않았다. 진단용 `uncaughtException` 수집기를 테스트 프로세스에 붙여 예외를 기록했다. 원본 앱 소스는 변경하지 않았다.

관찰 결과는 `windowId=1`, `isVisible()=true`, `isCrashed()=true`였다. 숨김 상태 변경 도중 예외가 발생해 실제 hide까지 도달하지 못했고, reveal도 같은 예외로 실패했다. 자동 재생성만 없는 문제가 아니라 기존 숨김·복원 처리가 깨진다.

### 원인과 영향

- [`sendOverlayState()`](../../src/main/main.ts)는 WebContents의 `isDestroyed()`만 확인한 뒤 `contents.mainFrame`을 읽는다. WebContents 객체가 남아 있어도 Renderer 종료로 frame은 사라질 수 있다. 핵심 위치는 `src/main/main.ts:56`이다.
- `render-process-gone → hideOverlay → updateOverlayState → sendOverlayState`에서 예외가 나면 `overlay.hide()`가 실행되지 않는다 (`main.ts:175`, `main.ts:443`).
- `reveal → updateOverlayState`에서도 동일하게 실패해 `showInactive()`까지 도달하지 않는다 (`main.ts:167`).

앱을 완전히 종료하고 같은 저장 경로로 다시 실행하면 revision 1·잔액 $99·같은 플레이어 카드로 복원됐다. 이 재현에서는 저장된 판·잔액 손실이 없었지만 앱 내 복원이 실패해 프로세스 재시작이 필요했다.

### 최소 수정 방향과 완료 조건

소실된 frame·종료된 Renderer에 상태를 보내지 않도록 방어하고, 상태 push 실패가 실제 hide/reveal 처리를 중단하지 않게 한다. 죽은 Renderer의 복원은 기존 창 표시만 시도하지 말고 저장된 Main 상태로 다시 로드하거나 필요한 최소 재생성 경로를 제공한다. 구 S16의 전체 장애 복구 설계를 다시 도입할 필요는 없다.

재현 E2E는 Main 예외 없음, 장애 후 숨김/복원 가능, 복원된 판·잔액 유지, 중복 창·정산 없음까지 확인해야 한다.

## 3. BUG-02 — 큰 금액 정산 오류 후 재시도 불능

### 발생 조건과 재현

검증기가 허용하는 큰 정수 센트 값을 격리된 저장 파일에 넣었다. 일반 사용자 자금은 사용하지 않았고, 정상적인 $100 시작에서 이 잔액에 도달하는 발생 빈도도 주장하지 않는다.

```text
balanceCents = 6,000,000,000,000,000  ($60,000,000,000,000)
pendingBetCents = 5,000,000,000,000,000  ($50,000,000,000,000)
카드 순서 = 10♠, 10♣, 9♦, 6♥, 2♠
```

1. 위 상태를 앱에서 정상 로드한다.
2. UI에서 딜한다. 플레이어 19, 딜러 공개 10이며 베팅이 차감되고 playerTurn으로 진행된다.
3. 스탠드를 누른다. 딜러가 16에서 2를 받아 18이므로 플레이어 일반 승리를 정산하려 한다.
4. 반환금 `wager × 2`가 안전 정수 한도를 넘는다.

관찰된 상태와 응답:

```text
phase: dealerTurn
revision: 2
balanceCents: 1,000,000,000,000,000
saveError: true
retrySave → INVALID_ACTION / No failed save to retry
```

같은 userData로 앱을 다시 실행해도 dealerTurn 정산이 다시 실패한다. UI의 저장 재시도 버튼을 직접 눌러도 `No failed save to retry`가 표시되고 버튼만 계속 남았다.

### 원인과 영향

- [`validateBet`](../../src/core/betting.ts)는 베팅 자체의 안전 정수·최소 금액·잔액만 검사하며 지급 시 산술 범위를 확인하지 않는다 (`betting.ts:2`).
- [`normalWinReturn`](../../src/core/settlement.ts)의 안전 정수 검사는 정상적으로 overflow를 거부한다 (`settlement.ts:31`). 문제는 이미 진행된 판에서 처음 이 오류를 발견한다는 점이다.
- [`GameStore.advanceDealer`](../../src/main/game/game-store.ts)는 transition 계산과 저장을 같은 catch로 처리한다. transition이 pending 생성 전에 실패해도 `saveFailed=true`로 표시한다 (`game-store.ts:127`, `game-store.ts:136`).
- pending이 없는 `retrySave`는 `No failed save to retry`로 거부하고 (`game-store.ts:64`), [Renderer](../../src/renderer/main.tsx)는 saveError일 때 저장 재시도만 보여 준다 (`main.tsx:345`).

이 재현은 극단적인 금액의 경계 결함이다. 일반 플레이에서 흔한 문제처럼 설명하지 않는다. 다만 내부 전이 오류를 저장 오류로 잘못 분류하는 원인은 금액 overflow에만 한정되지 않는다.

### 최소 수정 방향과 완료 조건

베팅 차감 전에 해당 규칙의 최대 지급과 최종 잔액을 안전하게 계산할 수 있는지 확인한다. 블랙잭 3:2·보험·더블·스플릿의 추가 행동도 포함해, 단순한 화면 상한만으로 처리하지 않는다.

내부 규칙/무결성 오류와 실제 파일 저장 실패를 구분하고, pending이 없으면 작동하지 않는 저장 재시도만 제공하지 않는다. 이미 저장된 문제 상태도 원본을 보존하며 명시적인 복구 선택을 할 수 있어야 한다. 임의 환급·자동 초기화로 덮지 않는다.

재현 E2E는 위험한 베팅/추가 행동의 사전 거부, 기존 판·금액 보존, 내부 오류 시 정확한 안내·복구 경로, 실제 저장 실패 재시도 유지까지 확인해야 한다.

## 4. 개선 후보 — 시작 시 파일 읽기 오류 안내

격리된 `session.json`을 읽을 수 없게 하고 유효한 `session.backup.json`을 둔 상태에서 패키지를 실행했다. `EACCES`를 stderr에 기록한 뒤 exit code 0으로 종료했고 백업은 보존됐다.

[`readValidated`](../../src/main/persistence/session-repository.ts)는 ENOENT 외 파일 I/O 오류를 전달하며 (`session-repository.ts:105`), [`start()` 실패 처리](../../src/main/main.ts)는 로그 후 종료한다 (`main.ts:463`). 백업 검사와 창·트레이 생성 전에 종료되는 경로다.

읽기 권한 문제를 사용자가 해결해야 할 수 있으므로 백업 자동 덮어쓰기를 해결책으로 삼지 않는다. “왜 앱이 실행되지 않는지” 알려 주고 일시 오류 재시도를 제공하는 개선은 가치가 있지만, 이번에는 데이터 손상·잘못된 정산과 같은 치명적 결함으로 분류하지 않는다.

## 5. 문제로 확인되지 않은 경로

- **일반 저장 실패·재시도:** 임시 저장 디렉터리의 쓰기를 막고 베팅 올리기를 눌렀다. 저장 실패 동안 화면·파일 모두 revision 0·베팅 $1·잔액 $100을 유지했다. 권한 복원 후 UI 재시도에서 revision 1·베팅 $2·잔액 $100으로 정확히 한 번 반영됐다. 저장 오류 UI도 정상 해제됐다.
- **일반 정산의 잔액 보존:** 고정 난수 seed로 600판, 2,181개 기록된 행동 전이를 확인했다. 히트·스탠드·더블·스플릿·보험·이븐 머니·서렌더를 포함했고, 원래 잔액 + 과거 순손익 − 현재 투입금 + 현재 반환금이 각 상태의 잔액과 일치했다. 이는 하위 계층의 보조 점검이며 모든 규칙 조합이나 UI 완주를 증명하지 않는다.
- **단일 인스턴스·명령 경합·신뢰 경계:** 관련 방어 코드와 기존 테스트를 읽었으며 이번 조사에서 확정된 신규 결함을 찾지 못했다. 해당 E2E 전체를 다시 실행한 것은 아니다.
- **Renderer 장애 후 디스크 상태:** BUG-01에서 완전 재실행하면 저장된 카드·revision·잔액을 그대로 읽었다. 장애 처리 결함과 저장 손실을 구분한다.

## 6. 재현 환경과 한계

- macOS 26.4.1 arm64, Node 22.22.1, Electron 44.3.0.
- 소스보다 기존 산출물이 오래돼 로컬 Electron ZIP을 사용하는 `npm run package`로 현재 프로덕션 패키지를 다시 만들었다. 빌드 성공.
- 실제 실행 파일: `out/molsino-darwin-arm64/molsino.app/Contents/MacOS/molsino`.
- 진단 스크립트·결과·저장 데이터: `/private/tmp/molsino-n01-audit-vTx094/`. `repro.cjs`·`results.json`, `extra-repro.cjs`·`extra-results.json`, `core-audit.mjs`·`core-results.json`을 사용했다. 임시 경로이므로 장기 재현은 위 조건을 기준으로 정식 E2E를 작성한다.
- 패키지 재현은 Playwright Electron의 실제 UI·IPC·Main·디스크를 사용했다. 기존 정식 E2E 전체 스위트나 N01 수정 후 완료 검증을 실행한 것은 아니다.
- 기본 sandbox에서 GUI 앱 실행이 실패해 격리 테스트 실행에 필요한 승격을 사용했다. 실제 사용자 userData는 읽거나 수정하지 않았다. 임시 디렉터리의 권한 변경은 실험 뒤 복구했고 실행한 테스트 앱은 종료했다.
- 앱 소스·기존 테스트 코드는 변경하지 않았다. 재현 과정에서 진단 스크립트의 상태 선택자 충돌도 수정했으나 이는 앱 결함이 아니다. 실제 OS UI 관찰 권한이 없어 오류 대화상자의 모양·물리 단축키·트레이 클릭은 검증하지 않았다.

## 7. 다음 작업 제안

사용자는 두 재현 조건이 일반 사용에서 쉽게 발생하지 않는다는 점을 근거로 N01 버그 수정 세션을 삭제했다. 실제 결함·재현 기록은 보존하되 우선 수정 권고와 후속 수정 일정은 철회한다. 다음 작업은 [현재 로드맵](../work-session-roadmap.md)의 N02 바카라 구현이다. 이번에는 문서만 변경했다.
