# 바카라 기술 설계

**목적:** 바카라 규칙을 공용 잔액·저장·IPC와 연결하는 경계를 정의한다.

**요약:** 독립된 순수 바카라 코어와 게임 어댑터를 두고 Main의 공용 작성자가 베팅·자동 진행·정산·최근 기록을 원자적으로 저장한다. 규칙은 제품 설계, 앱 저장 형식은 메인 기술 설계에서 관리한다.

## 1. 구현 상태와 책임

`BaccaratCore`는 Electron·DOM·타이머·파일에 의존하지 않는 순수 TypeScript 전이다. 점수·세 번째 카드·배당·슈 운영은 [제품 설계](product-design.md)를 따른다. 블랙잭의 312장 검증기·점수·정산 상수를 바카라에 적용하지 않는다.

공용 `AppStore`(책임 이름)는 [메인 기술 설계 §9](../../main/technical-design.md#9-여러-게임과-공용-잔액의-신규-계약)에 따라 게임 상태와 잔액을 함께 확정한다. 카드 모델·검증된 순수 셔플은 필요한 경우 추출해 공유하지만 게임 규칙은 독립시킨다.

## 2. 게임 상태와 명령

바카라 상태는 `ruleSetId`, `shoe`, `pendingBet { target, amountCents }`, `round`, `lastResult`, `recentResults`와 정산 식별 정보를 가진다. `ruleSetId`는 `baccarat-8d-commission5-tie8-v1`로 고정한다. 잔액은 공용 wallet에만 저장한다.

- `round`는 roundId, 베팅 대상·원금, Player/Banker 카드, 진행 단계, 정산 여부를 보존한다.
- 저장 phase는 `betting | dealing | result`다. dealing의 내부 단계는 `initial | playerThird | bankerThird | settle`로 구분한다.
- `recentResults`는 최대 20개의 `{roundId, outcome: 'P' | 'B' | 'T'}`이며 결과 저장과 함께 갱신한다. 최신 결과의 roundId와 중복·순서를 검증한다.
- 사용자 명령은 `setBet`(대상과 금액의 원자 변경), `deal`, `nextRound`다. 메뉴·새 시작·저장 재시도는 앱 공통 명령이다. 한 번의 setBet에 복수 대상이나 알 수 없는 필드를 받지 않는다.
- Main 전용 내부 명령은 `advanceBaccarat`다. 공개 IPC에서 직접 호출할 수 없다. Main은 진행 가능한 내부 단계에서만 정확히 한 번 예약한다.

## 3. 배분과 정산

1. deal은 금액·대상·공용 잔액·안전 정수 범위·진행 중 게임을 검사하고 필요 시 새 슈와 버림을 준비한다.
2. 베팅 차감·roundId·dealing/initial·게임 잠금을 한 후보로 만들어 저장한다. 실패하면 차감 성공으로 표시하지 않는다.
3. 첫 내부 전이는 네 장을 정해진 순서로 배분하고 내추럴을 판단한다. 이후 Player 세 번째 카드, Banker 세 번째 카드, 정산 순서로 필요한 단계만 진행한다. 카드를 받지 않는 단계도 결정론적으로 다음 상태를 계산한다.
4. 정산 전이는 결과·총 반환금·순손익·공용 잔액·정산 키·최근 기록·result phase·게임 잠금 해제를 함께 저장한다.
5. 저장 성공 후 공개 상태를 push하고 다음 내부 단계가 있으면 한 번 예약한다. Renderer 애니메이션의 완료 신호를 기다리지 않는다.

금액은 정수 센트다. Banker 이익은 정수 산술로 `floor(wagerCents × 95 / 100)`에 나머지가 50 이상이면 1을 더한다. 중간 곱·총 반환·잔액 덧셈 모두 안전 정수를 검사한다. 정산 도중에만 overflow를 발견해 판이 멈추지 않도록 deal 때 선택 대상의 최대 반환과 최종 잔액을 사전 검사한다.

정산 키는 `(sessionId, gameId, roundId, componentId='main')`다. 이미 확정된 판은 같은 지급·기록을 적용하지 않는다. 최근 20개 표시 기록을 무결성 원장 전체로 사용하지 않는다. 삭제된 옛 표시 기록과 별개로 현재 판의 정산 증거·commandId/revision 검사가 중복 실행을 막는다.

## 4. 저장·공개 상태·복구

상태 검증은 416장 구성·카드 ID 고유성·소비 prefix·버림 인덱스·패당 최대 세 장·세 번째 카드 규칙·phase·베팅·정산·최근 기록의 일관성을 확인한다. 부족한 슈를 판 중 재셔플로 덮지 않는다. 불일치는 복구 오류로 보고하고 임의 환급·재정산을 하지 않는다.

공개 상태에는 공용 잔액, 현재 phase, 베팅 대상·금액, 공개 카드·점수, 결과·순손익, 최근 20개 결과와 허용 동작만 담는다. 슈·버린 카드·미래 카드·내부 난수·정산 관리 정보를 내보내지 않는다. 카드가 아직 배분되지 않은 단계는 카드가 있는 것처럼 표시하지 않는다.

정상/강제 종료 후 저장된 dealing 단계에서 자동 진행을 재개한다. 저장 실패는 같은 후보를 보존해 재시도한다. 정산 저장 성공 후 응답 유실·reload·메뉴 재진입은 result를 표시할 뿐 지급·최근 기록을 추가하지 않는다. 앱 공통 형식의 primary/backup·손상/미래 버전 복구 정책을 재사용하며 별도 바카라 지갑 파일은 만들지 않는다.

## 5. 검증 경계

순수 규칙표·금액 경계·불가능한 상태는 하위 테스트로 보조하고, 공식 세션 완료는 [바카라 E2E 설계](e2e-test-plan.md)를 따른다. N02에서 패키지의 실제 제한 API와 공용 저장을 통한 통합, 실제 화면 클릭과 두 게임 왕복을 모두 확인한다. 테스트 픽스처는 격리된 userData·테스트 실행 조건에서만 활성화하고 일반 게임 선택의 준비 중 제한을 우회하는 공개 API를 만들지 않는다.
